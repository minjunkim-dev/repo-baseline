# 범용 PR 품질·문서·CI/CD 셋업 프롬프트

이 프로젝트에 PR 품질·문서·CI/CD 운영 기준을 실제로 적용하고 검증해줘.
1인 개발 기준이다. 실제 언어·디렉터리·기준 브랜치·기존 도구와 배포 단위를 사용해. 이 문서의 main은 실제 기준 브랜치를 뜻한다.
Bugbot은 수동 보조 리뷰다. Autofix와 On-demand는 Off로 유지해. 공개 배포·production 변경·유료 서비스 활성화는 금지한다.
구체적인 공통값은 `minjunkim-dev/repo-baseline`의 `POLICY.md`와 `templates/`를 따른다. 공통 검사기는 그 저장소의 `scripts/`를 `tools/apply_baseline.py`로 복사한다. 복사본은 프로젝트에서 직접 고치지 마.
계획이나 제안에서 멈추지 말고 승인된 파일 변경·독립 리뷰·필수 CI·위험별 main 반영을 완료해.

## 1. 두 번째 요청의 시작과 완료

같은 채팅에서 GitHub 설정 프롬프트 다음에 이 프롬프트를 적용한다. 두 파일을 처음부터 함께 적용하라고 요청했으면 GitHub 초기 점검을 먼저 마쳐.
이 작업은 저장소 파일 변경·실행 검증을 맡는다. 마지막에는 앞서 승인된 GitHub 설정 기준으로 보류 항목을 완료하고 재조회한다. 세 번째 프롬프트를 요구하지 마.

1. 이전 인계 기록의 대상 저장소·현재 설정·보류 항목·권한·CI·배포·Bugbot 근거를 확인해. 같은 저장소인지 대조해. 변경된 상태와 오래된 실행 근거만 갱신해.
2. 문서·코드·workflow·검사기·지원되는 설정 파일을 구성해. 최종 전체 diff의 독립 리뷰와 실제 PR CI를 확인해.
3. 이전 GitHub 프롬프트의 기준으로 검증된 체크를 등록하고 영향받는 보호·옵션을 재조회해. 위험별 승인 후 정확한 최종 head를 병합해. main CI를 확인하고 인계 목록을 종료해.

GitHub 설정 프롬프트나 이전 기록이 없으면 누락을 기록하고 승인된 로컬 작업을 계속해. 서버 설정을 완료했다고 추측하지 마. 필수 보호가 미검증이면 자동 병합하지 마.
설정 기준은 GitHub 프롬프트, 파일 구현·로컬 리뷰·수동 시험 기준은 이 프롬프트가 관리한다. Bugbot 옵션 목록을 여기에 중복 유지하지 마.

## 2. 현재 상태·작업 범위·스킬

- 실제 Git remote·기본 브랜치·스택·Issue 규칙·현재 CI/CD를 확인해. 열린 PR·worktree·dirty 상태를 확인하고 다른 작업자의 변경을 보존해. 적절한 깨끗한 worktree를 재사용하거나 필요한 경우 격리해.
- branch push·PR 생성·main 병합 전에 공개 자동 배포 연결을 확인해. 공개 배포를 유발하는 동작은 보류해. 기존 배포 pipeline·production 설정·보호를 임의로 해제하지 마.
- 실제 구현된 빌드·테스트·패키징 단위에 맞춰 적용해. 존재하지 않는 플랫폼의 구현·기기·배포를 검증했다고 보고하지 마.
- ChatGPT/Codex Cloud 계정과 서비스 저장소 목록은 탐색하지 마. 대상 저장소의 실제 자동 리뷰 연결은 GitHub 인계 기록을 사용해. 필요한 최신 상태만 다시 확인해.
- 설치된 관련 스킬의 실제 지침을 확인해. 사용자 경로와 대체 설치 경로를 확인하고 미확인과 미설치를 구분해. 사용하지 않은 스킬이나 리뷰를 실행했다고 보고하지 마.
- 필요한 Matt Pocock 스킬을 선택해. 구현에는 tdd·diagnosing-bugs·codebase-design, 독립 리뷰와 PR에는 code-review·pr, 미확정 결정에는 grilling·research·domain-modeling을 사용해. 문서에는 writing-for-agents, 반복 문제의 환경 개선에는 설치된 retro를 활용해. 모든 스킬을 강제로 실행하지 마. 깊은 모듈 개선은 확인한 문제와 합의한 범위에서만 진행해.

## 3. AGENTS.md와 상세 문서

1. AGENTS.md를 공통 길잡이로 정리해. 프로젝트 식별·작업별 문서 경로·제품 결정·승인 경계만 짧게 남겨.
2. 구현 에이전트는 확정 Issue·완료 조건·필요한 코드와 도메인·작업 절차를 읽게 해. 전체 코딩 규칙과 리뷰 체크리스트를 구현 시작마다 상시 주입하지 마.
3. 코딩·설계 기준과 P0/P1/P2 판단은 별도 코딩 규칙에 둬. 리뷰 입력·보고·수정·검증·병합은 별도 리뷰 문서에 둬. Issue·협업·검증 명령은 작업 문서에 둬. 실제 기존 파일을 재사용해. docs/coding-standards.md·docs/agents/review.md 등은 역할의 예시이며 고정 경로가 아니다.
4. 원문·제품·보안·권리·접근성·기기 검증·작업 시작 preflight·위험별 승인 기준을 보존해. README·CONTRIBUTING·스크립트·테스트의 이동 경로와 anchor를 확인해.
5. 추적된 CLAUDE.md와 도구별 중복 지침의 고유 내용을 옮긴 뒤 정리해. shim·symlink를 다시 만들지 마. 개인·전역·관리자 지침은 보존해.
6. 기존 피처 플래그·데이터 호환·OFF/ON·접근성 계약을 보존해. 미완성 기능을 병합하면 실제 진입점의 기본값을 OFF로 두고 담당자·완료 조건·제거 조건을 기록해. 사용처 없는 공통 플래그 체계를 만들지 마.
7. 사용하는 도구의 AGENTS.md 로딩 지원을 확인해. 자동 로딩을 확인할 수 없으면 시작할 때 명시적으로 읽는 절차를 문서화해. 실제 실행하지 않은 로딩을 검증했다고 보고하지 마.

## 4. CI·보안 분석·설정 파일 구현

1. 기존 lint·typecheck·테스트·빌드·보안·dependency 검사를 조사해. 적절한 검사는 재사용하고 누락·미연결을 보완해. 전체 포맷·불필요한 dependency·범위 밖 리팩터를 섞지 마.
2. 호출자의 공개 interface에서 정상·실패 동작을 검사해. 상수 재단언·소스 문자열 순서·실패를 지운 mock으로 초록 CI를 만들지 마. 정적 제약에는 정적 검사를 사용해. 단순 문서 이동을 복제하는 테스트는 추가하지 마.
3. aggregate는 실제로 선택된 job의 실패·취소·누락을 거부하게 해. 불필요한 job의 skip은 명시된 범위 정책으로 처리해. 기존 체크 이름·publisher·신뢰하는 base·trusted aggregation을 보존해.
4. GitHub 인계 목록의 CodeQL·Dependabot·Action SHA·최소 권한·읽기 전용 감사·Bugbot YAML 요구조건을 파일 작업으로 구현해. 지원과 호환성은 해당 GitHub 프롬프트 기준을 사용해. source 실행·분석·업로드를 실제로 확인해. 미지원 언어와 제품 SDK를 억지로 변경하지 마.
   공통 검사기·테스트는 `repo-baseline`에서 적용하고 `.github/repo-baseline.json`에 원본 commit과 해시를 기록해. 복사한 테스트가 기존 필수 CI job에서 실행되는지 확인해. 프로젝트 고유 값(Bugbot 규칙 경로·테스트 위치)은 manifest에만 둬.
5. PR 코드는 Secret·높은 권한과 분리해. 읽기 빌드와 쓰기 게시를 분리해. 새 권한·Secret·신뢰 경계 변경은 검토 가능한 최종 head를 준비하고 사람 승인을 받아.
6. 체크 이름이나 trusted base 정책을 바꾸면 기존 보호에서 통과할 수 있는 전환 PR을 먼저 준비해. 유효한 기존 체크를 유지하며 새 체크를 검증해. 검사를 우회하거나 임시로 보호를 낮추지 마.
7. source와 정책이 유효한 동일 head/base의 통과 근거를 재사용해. 새로운 변경·실패·입력 변경이 없으면 테스트와 서버 조회를 중복 실행하지 마.

## 5. 독립 리뷰·직접 수정·CI 실패 처리

기본 흐름은 로컬 구현 → 결정적인 검사 → 별도 Standards·Spec 리뷰 → 확실한 결함 수정·커밋 → 최종 전체 diff 리뷰·필수 CI다.

1. 실제 PR base와 최종 head SHA·전체 diff·확정 완료 조건·실행 근거·필요한 문서를 고정해. 다른 작업과 무관한 커밋을 포함하지 마.
2. 작성자와 분리한 컨텍스트에서 Standards와 Spec을 각각 실행해. Standards는 코딩 규칙을 읽는다. Spec은 확정 완료 조건과 관련 계약을 읽는다. 권한·Secret·인증·외부 명령·삭제·dependency·workflow 신뢰 경계는 별도 Security 리뷰를 추가해.
   권한·Secret·workflow·저장소 설정·dependency 정책을 바꾸는 PR에는 작성자와 다른 모델의 리뷰를 추가해. 다른 모델을 쓸 수 없으면 그 사실을 기록하고 사람 승인 여부를 위험 기준으로 판단해.
3. 직접 수정할 파일의 소유권을 구분해. 확실한 결함은 승인된 범위에서 수정하고 커밋해. 다른 작업을 되돌리지 마. 불확실하거나 범위 밖인 지적은 근거와 함께 보고해.
4. P0/P1은 해결해. P2는 수정하거나 프로젝트 정책에 따라 후속 Issue와 이유를 남겨. 수정 후 영향받는 검사와 최종 전체 diff를 다시 확인해.
5. 리뷰의 실제 base/head·문서 fingerprint·컨텍스트·모델·결과·수정 커밋을 기록해. 같은 모델이면 같은 모델의 별도 컨텍스트라고 기록해. 실제 독립 리뷰가 없으면 완료로 표시하거나 자동 병합하지 마.
6. 맡은 PR의 CI가 끝날 때까지 확인해. 실패하면 head/base·run ID·attempt와 실패 로그를 기록해. 코드 결함·환경 문제·일시적 장애를 구분하고 가능한 실패를 로컬에서 재현해.
7. 원인을 수정하고 관련 검사 후 커밋·푸시해. 새 최종 head의 독립 리뷰와 필수 CI를 확인해. 검사 삭제·skip·assertion 완화로 실패를 숨기지 마. 근거 없이 재실행만 반복하지 마. 재시도로 해결됐으면 원인·확인 한계를 기록해.

PR 본문에는 Summary의 변경 이유와 before/after 또는 작은 도식, Evidence의 실제 명령·결과·SHA·미확인 범위, Merge Danger의 문 유형·영향 범위·복구 방법을 남겨. 긴 설명이나 위험 점수로 근거를 대신하지 마.
저장소에 PR 양식이 있으면 그 제목 구조와 필수 항목(관련 Issue 또는 생략 이유, 플래그 상태 등)을 지켜. 병합 직전에 본문을 양식과 대조해. Dependabot PR에는 사람용 양식을 강제하지 마.
반복된 실제 지적은 재현 검사·자동 체크·코딩 규칙으로 옮겨. 경로 탐색 문제는 AGENTS의 안내를 고쳐. 확인하지 않은 가상 문제의 검사와 자동화를 추가하지 마.
이 절차는 담당 세션의 작업이다. 별도 상시 감시 서비스를 구축했다고 보고하지 마.

## 6. Bugbot 핵심·영역 규칙과 크기 검사

Bugbot에는 핵심·변경 영역 규칙만 전달해. 상세 원문과 로컬 독립 리뷰의 역할을 보존해.

1. 코드 구조와 실제 검토 경계를 조사해. root `.cursor/BUGBOT.md`에는 공통 핵심 규칙을 짧게 요약해. 실제 결함·실패 조건·영향·최소 수정안·정상/실패 테스트·비밀정보·권한·증거 범위를 포함해.
2. 필요한 영역에만 하위 `.cursor/BUGBOT.md`를 배치해. 해당 경로 변경에 필요한 요약만 둬. root에서 모든 영역을 링크하지 마. 상세 코딩 규칙이나 원문을 복제하지 마.
3. 상세 문서·다른 영역 규칙으로 향하는 로컬 Markdown 링크와 일괄 읽기 지시를 제거해. 우회 링크로 전체 문서를 수집하지 마. 부족한 자료는 미확인으로 보고하게 해.
4. 상세 원문을 보존해. 로컬 리뷰 문서에 변경 영역별 자료 선택 표를 둬. 리뷰어가 코딩 규칙·티켓 조건·필요한 도메인·ADR·검증·배포·권리 원문만 읽게 해. 실제 경로를 확인해.
5. 기존 검사기를 재사용하거나 최소한으로 보완해. 규칙 하나는 30,000자 이하, 모든 추적된 root·영역 규칙 합계는 95,000자 이하로 검사해. 공식 제한은 적용 전에 확인해. 95,000자는 공식 전체 한도 100,000자보다 여유를 둔 저장소 정책이다. 한도 변경이 필요하면 근거를 보고해. 통과를 위해 임의로 올리지 마.
6. 상세 원문 길이는 예산에서 제외해. 필수 root/영역 파일 누락·빈 파일·symlink·저장소 밖 경로·상세 문서의 로컬 링크를 거부해. 새 영역을 추가하면 필요한 목록을 갱신해.
7. 실제 임시 저장소·파일·CLI로 경계값·1자 초과·합계 초과·영역 누락·문서 재연결·경로 안전 실패를 확인해. 상세 원문 증가가 규칙 예산에 들어가지 않는지 확인해.
8. 기존 repository 검사나 필수 CI 경로에 연결해. 이전 trusted base 검사기가 상세 문서 연결을 필수로 요구하면 정책 전환 PR과 규칙 축소 PR로 나눠. 각 PR의 독립 리뷰·CI를 확인해. 검사를 우회하지 마.

모든 영역의 정적 합계는 특정 PR의 실제 입력보다 보수적이다. 팀·학습 규칙과 서버 포함을 로컬 합계만으로 증명하지 마.

## 7. Bugbot 수동 시험과 로컬 수정

1. GitHub 인계 기록에서 같은 저장소의 Manual Only·Autofix Off와 On-demand Off의 유효한 실제 근거를 확인해. 변경된 상태만 재조회해. 파일만으로 대시보드·결제 상태를 증명하지 마.
2. 추가 과금 없이 시험할 수 있는 근거를 확인해. On-demand Off만으로 무료 실행을 가정하지 마. 비용·권한·연결을 확인하지 못하면 시험을 보류하고 미확인 범위를 남겨. 규칙·독립 리뷰·CI 작업은 계속해. 구독·체험·Autofix·On-demand를 활성화하지 마.
3. 준비한 설정이 어느 브랜치에서 실제 적용되는지 확인해. main 반영이 먼저 필요한 설정은 안전하게 반영·검증한 뒤 적절한 기존 PR이나 승인된 검증 PR에서 시험해. 해당 PR을 시험 목적으로 병합하지 마.
4. 실행 가능한 승인된 PR에서 공식 지원 트리거로 수동 리뷰를 한 번 요청해. verbose를 지원하면 핵심·해당 영역 규칙의 포함·생략·잘림을 확인해. 요청 PR·검토 head·요청 ID/코멘트 ID·시각·실제 리뷰·요약·관측 사용량을 기록해.
5. 실제 결함·오탐·판단 보류로 분류해. 확실한 결함만 로컬에서 수정하고 커밋해. 변경한 최종 head의 전체 diff 독립 리뷰와 필수 CI를 다시 확인해.
6. 요청 댓글·neutral·지적 0건을 리뷰 완료·무결함의 증거로 사용하지 마. 한 PR의 규칙 표를 전체 영역의 서버 검증으로 확대하지 마. 정적 검사·main 반영·서버 포함·사용량을 구분해. 서버 시험은 선택적 보조 검증이며 필수 CI를 대체하지 않는다.

연결·옵션 기준은 GitHub 프롬프트가 관리한다. 같은 채팅의 승인된 설정 작업으로 필요한 확인을 마무리해. 다른 계정·프로젝트의 연결을 바꾸지 마.

## 8. CI/CD와 미공개 산출물

1. 실제 제품의 기존 빌드·패키징·배포 단위를 조사해. 같은 Release workflow를 모든 프로젝트에 강제하지 마. 필요가 없으면 근거와 함께 비해당으로 기록해.
2. 산출물이 필요하면 version과 정확한 source SHA를 받는 수동 미공개 Draft workflow 또는 동등한 미공개 artifact 절차를 준비해. source SHA 유효성·기준 브랜치 포함·같은 SHA의 필요한 CI·버전 형식과 중복을 검증해.
3. 빌드와 쓰기 게시를 분리해. version·source SHA·도구 버전·checksum을 남겨. 기존 Release·태그·asset을 덮어쓰지 마. 쓰기 전에 입력과 근거를 확인해. 새 쓰기 권한은 최종 head의 사람 승인 후 반영해.
4. 기본 셋업에서는 workflow 준비·입력 실패 검사·허용된 로컬 빌드와 패키지 검증까지 수행해. 원격 Draft 생성·tag 쓰기·업로드·배포 실행을 준비 완료와 혼동하지 마.
5. 실제 미공개 Draft 생성·다운로드·smoke는 사용자가 구체적인 version/source SHA와 실행을 승인한 경우에만 수행해. 입력을 추측하지 마. 실행 승인이 없으면 필요한 입력과 미실행 범위를 보고해.
6. 승인된 실행에서는 새 미공개 상태·대상 source·산출물 version·재다운로드 checksum·내용·가능한 최소 실행을 확인해. 공개 Release·스토어 제출·공개 registry push·production 배포는 이 셋업에서 실행하지 마.

Environment의 서버 설정은 GitHub 기준을 따른다. 실제 승인/Secret 경계가 필요한 job에만 연결해.

## 9. 격리 CI 실패·복구 시험

현재 코드·정책·CI·보호에 유효한 기존 실패/복구 근거를 확인해. 유효하면 재사용해.
근거가 없거나 해당 정책이 바뀌었으면 격리 브랜치와 Draft PR에서 최소한의 실제 검사 실패를 시험해.

1. 공개 자동 배포가 없고 main·Secret·실제 데이터·외부 발송을 건드리지 않는 시험을 준비해.
2. 정상 baseline → 기존 검사가 잡는 작은 실제 결함 → 필수 체크 실패와 병합 차단을 확인해. 실패 head·base·run/attempt·로그를 기록해.
3. 로컬에서 재현·수정하고 관련 검사를 실행해. 수정 커밋의 최종 전체 diff 독립 리뷰와 필수 CI 성공을 확인해. 제품 helper와 검사 설정을 정상으로 복구해.
4. 검증 PR은 병합하지 마. auto-merge를 예약하지 마. 한 종류의 시험으로 모든 플랫폼·장애를 검증했다고 보고하지 마.

새 품질 게이트를 연결하기 위해 정상 PR 검증과 필수 체크 등록을 먼저 완료할 수 있다. 새 workflow나 trusted policy의 main 반영이 필요하면 정상 셋업 PR의 독립 리뷰·위험별 병합·main 검증을 먼저 마친 뒤 격리 시험을 수행해. 셋업 PR의 자체 합격 조건과 전체 셋업의 복구 시험 완료 조건을 구분해. 실패 시험은 보호가 실제 적용된 뒤 수행해. 시험을 위해 main이나 보호를 깨뜨리지 마. 전체 셋업 완료는 필요한 격리 시험까지 확인한 뒤 판정해.

## 10. GitHub 최종 적용·위험별 병합·완료 보고

1. 앞서 승인된 GitHub 프롬프트와 인계 목록으로 검증된 체크와 필요한 설정을 완료해. 같은 채팅에서 처리해. 계정 전체 재탐색과 유효한 설정 전체의 재적용을 반복하지 마. 새 권한·신뢰 경계·범위 확대는 구체적 근거로 필요한 승인을 받아.
2. 실제 최종 head/base·독립 리뷰·필수 CI·티켓 완료 조건·미해결 지적·대화 해결·보호를 확인해. trusted aggregation이 있으면 source run·attempt·workflow ID/path·head/base/merge/policy SHA와 accepted 판정을 확인해.
3. 위험이 낮고 되돌리는 방법이 명확하며 영향 범위가 좁은 양쪽 문은 이 요청에서 병합을 위임한다. 위 조건을 모두 충족하면 직접 병합해. 한쪽 문 또는 넓은 영향은 사람이 최종 head와 영향을 승인한다.
4. 데이터 삭제·복구가 어려운 migration·Secret/인증/권한/신뢰 경계·새 workflow 쓰기 권한·대량 발송·복구 불확실은 위험 변경이다. GitHub 승인 0명은 이 사람 승인을 없애지 않는다. GitHub가 같은 계정의 사람과 에이전트를 구분한다고 주장하지 마.
5. 병합 직전에 GitHub의 실제 head/base와 검사 결과를 재조회해. 검증 후 변경됐으면 영향받는 리뷰와 검증을 갱신해. --match-head-commit으로 정확한 head를 고정해. --admin이나 보호 해제로 우회하지 마. 모든 PR에 자동 병합을 예약하지 마. 자동 병합 예약은 최종 SHA의 독립 리뷰를 신뢰할 수 있는 필수 체크로 연결한 경우에만 별도로 구성해.
   다른 사람이나 봇의 PR 브랜치에 커밋을 추가하면 PR 댓글로 알려. 새 head의 독립 리뷰와 필수 CI를 다시 확인해. 이 push의 사람 승인 여부는 변경의 권한·신뢰 경계로 판단하고, 도구가 막으면 사용자에게 확인해.
6. main SHA·최종 파일·실제 main CI를 확인해. 실패하면 원인을 확인하고 승인된 범위에서 수정 PR 또는 revert로 복구해. 기존 보호를 유지해. 계정·권한 문제와 해결하지 못한 실패가 남으면 병합하거나 전체 완료로 표시하지 마.
7. 인계 목록의 종료·보류·미확인과 후속 항목을 기록해. 필수 CI와 독립 리뷰가 미검증이면 완료로 표시하지 마. 선택적 Bugbot·공식 미지원 분석·미승인 Draft 실행 때문에 검증된 필수 셋업까지 실패로 표시하지 마.
