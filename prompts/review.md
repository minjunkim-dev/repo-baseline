# 리뷰 프롬프트

PR을 연 뒤, 구현한 세션이 아닌 **새 세션**에 이 파일을 첨부한다. 하네스는 무엇이든 된다. 구현과 다른 도구·모델이면 더 좋다.
구현 세션이 띄운 하위 에이전트는 이 리뷰가 아니다. 기준을 고르고 결과를 받아들이는 쪽이 구현 세션이기 때문이다([POLICY.md](../POLICY.md) §3).

---

이 PR을 리뷰해 줘: `<PR 링크 또는 브랜치>`. 아래 순서대로 하고 「보고」 형식으로 끝내.

## 입력

- 변경분: `gh pr checkout <PR URL>`로 PR head 브랜치를 작업 트리에 받는다(fork PR도 된다). `gh pr view <PR URL> --json headRefOid,baseRefName`으로 head SHA와 base를 적어 두고, `git diff <base 원격>/<base>...<head SHA> -- . ':!.env*'`로 본다. `git status`가 깨끗하고 `git rev-parse HEAD`가 그 head SHA와 같을 때만 리뷰한다. 다르면 다시 받는다. 2라운드부터는 직전 리뷰 이후 바뀐 부분(직전 리뷰의 마지막 커밋부터 현재 head까지)만 본다. 그 사이 구현 쪽에서 push한 커밋도 포함한다.
- 기준: 저장소 루트의 `REVIEW.md`.
- 완료 기준: PR 본문 Summary의 `완료 기준:` 줄.
- Door와 신뢰 경계: PR 본문 Merge Danger. 본문을 믿지 말고 diff로 다시 정한다. 애매하면 되돌리기 어려움이다.
- 검사 명령: `AGENTS.md`의 check·test.

## 할 일

1. `REVIEW.md`의 「실패로 보는 것」과 완료 기준으로 diff를 본다. 근거가 필요하면 연결된 코드를 읽는다. 근거는 `file:line`이다.
2. Door가 되돌리기 어려움이거나 신뢰 경계 경로를 건드리면 보안 관점으로 한 번 더 본다.
3. 확실한 결함은 이 브랜치에 직접 고쳐 커밋·push하고, 영향받는 check·test를 다시 돌린다. push한 뒤 PR head SHA가 고친 커밋인지 확인한다. push하지 못했으면 고친 것으로 보고하지 말고 "PR에 미반영"으로 적는다.
4. 판단이 필요한 것은 고치지 말고 남긴다. 지적은 버그 유형으로 묶는다.
5. 「배운 규칙」에 있는 규칙을 어긴 곳이 있으면 그 규칙을 근거로 적는다.

## 하지 않는 것

- PR을 병합하거나 `main`에 push하지 않는다.
- 완료 기준 밖의 리팩터링·스타일 수정을 하지 않는다. 포매터·린터가 잡는 것은 보지 않는다.
- 이미 보고한 지적을 새 지적으로 다시 보고하지 않는다. 다만 이전 라운드의 남은 지적은 해결됐는지 확인하고, 해결되지 않았으면 「남은 지적」에 그대로 둔다.
- 비밀값 파일(`.env*`, 키)을 읽지 않는다. diff에 비밀값 파일이 걸리면 내용을 열지 말고 경로만 적는다.
- `REVIEW.md`의 「배운 규칙」을 직접 고치지 않는다. 필요하면 제안으로 보고한다.

## 라운드

- 최대 3라운드다. 3라운드 뒤에도 지적이 남으면 목록을 늘리지 말고 구현 방식을 다시 생각하라고 보고한다.

## 보고

보고 직전에 PR head SHA를 다시 확인한다. 리뷰를 시작한 뒤 바뀌었으면 추가 변경을 보거나, 보지 않은 커밋을 「남은 지적」에 "미검토"로 적는다.

PR 본문 Review 칸에 아래를 적는다. 본문을 고칠 수 없으면 보고만 한다.

```
리뷰어(구현과 다른 컨텍스트, 도구/모델): <도구> / <모델>, 라운드 <N>[, 보안 관점]
리뷰한 head와 Door: <커밋 SHA(직접 고쳤으면 고친 뒤의 마지막 커밋)>, <되돌리기 쉬움 | 되돌리기 어려움>
고친 것: P0 <N>, P1 <N>, P2 <N>. <유형별 한 줄과 커밋>
남은 지적: <없음 | 유형별 한 줄, 심각도, file:line>
확인한 것: <돌린 명령과 결과, 본 범위>
제안(반영 안 함): <배운 규칙 후보 등>
```
